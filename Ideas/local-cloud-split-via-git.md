# Расщепление задач локаль↔облако через гит

Паттерн для повторяющихся автоматизированных задач (cron/routine): как решить, где задача выполняется, и как связать локальную и облачную части, если данные живут в разных местах.

## Ключевой критерий: «облакопригодность»

Задачу можно повесить на облачный routine (cron-агент, работает без твоей машины) тем легче, чем больше **и вход, и выход** живут в гит-репозитории. Облачный агент видит **только репозиторий на момент клонирования** — не твою машину, не OneDrive, не локальные токены.

| Задача | Вход | Выход | Где живёт |
|---|---|---|---|
| Финансы (`/mail` → `/process-finance`) | вложения из почты | OneDrive (не гит) | **локально** — оба конца снаружи гита |
| Отчёты по волту diaries | заметки (в гите) + почта (не в гите) | файл отчёта (в гите) | **гибрид** — упирается в один внешний вход (почта) |
| Чистый отчёт только по волту | заметки (в гите) | отчёт (в гите) | **облако** — всё в гите |

Проверено 2026-07-11: волт diaries реально **пушится** в `git@github.com:redtigra/diaries.git` (0 непушнутых коммитов, плагин Obsidian Git коммитит+пушит). Значит облачный агент может его склонировать, прочитать, собрать отчёт и запушить обратно — сторона «хранилище» закрыта.

## Паттерн: тонкий локальный сборщик + облачный сборщик

Внешние сайд-входы (почта, OneDrive) почти никогда не переносятся в облако сами. Решение — **расщепить задачу**, а связью между частями сделать гит:

1. **Локальный шаг** (Windows Task Scheduler, на твоей машине): забирает внешний вход и **замораживает его в репозиторий как обычную заметку**, затем `git push`.
   - Механически это тривиально: `fetch_mail.py` **уже выводит письма в Markdown** (функция `format_messages`). «Сгрузить как заметку» = перенаправить тот же вывод в `.md`-файл волта вместо экрана:
     ```
     ...python.exe "...fetch_mail.py" --search "CBRE" --since 2026-07-06 > "...\diaries\2026\Mail\20260706-CBRE-mail.md"
     ```
   - Почта из «внешнего API-входа» превращается в «файл в репозитории» → облаку доступно.
2. **Облачный шаг** (routine по cron): работает **чисто из репозитория** — читает замороженную заметку, собирает отчёт, пушит результат. Живой доступ к почте ему не нужен.

Тогда каждый кусок работает там, где ему доступны данные, а «тяжёлую» часть (сборка/оформление) можно гонять в облаке по расписанию.

## Проблема тайминга и контракт свежести

Это **две задачи по расписанию на разных машинах**, и облачная читает только то, что локальная успела запушить. Порядок критичен.

Пример (недельный отчёт, пятница):
- **08:00** локальная: почта → запись `...mail.md` → push. В GitHub появляется свежий файл.
- **09:00** облачная: клонирует, видит свежий файл, собирает отчёт. ✅

Сбой порядка (облако в 09:00, а локальная в 10:00 / не отработала — ноут выключен, нет интернета):
- 09:00 облако клонирует → свежего файла ещё нет → читает **прошлонедельный** → отчёт по старью.
- 10:00 локальная пушит свежее — поздно, отчёт уже собран.

Аналогия: записка на холодильнике. Придёт читать раньше, чем ты написала, — прочитает вчерашнюю. Облако смотрит только на холодильник (GitHub), не на твою руку.

**Решение — таймстемп как проверяемый контракт.** В шапку замороженной заметки писать не «когда сгенерено», а **какую неделю покрывает**:
```
generated: 2026-07-12T08:03Z
covers: 2026-07-06..2026-07-12
```
Облачный шаг знает свой целевой диапазон (из даты запуска), читает `covers:` и **сверяет**. Совпало — собирает; лежит прошлая неделя — **останавливается с ошибкой**.

Важно понимать границу приёма: таймстемп даёт **обнаружить** несвежесть, а не **предотвратить**. Если локальная задача не отработала, отчёта всё равно не будет — но облако **честно упадёт**, а не выдаст правдоподобный отчёт по старью. «Громко упасть» лучше, чем «тихо соврать». Зазор в расписании всё равно нужен, чтобы в норме всё сходилось; таймстемп — страховка на сбой.

Тонкости выбора метки:
- Сверять по **покрываемому диапазону** (`covers:`), а не по «времени генерации» — клок-таймстемп заставляет облако гадать «достаточно ли свежо», а диапазон прямо отвечает «та ли это неделя».
- Самый крепкий вариант — опереться на **сам гит**: облачный шаг требует существования коммита, трогавшего файл этой недели. Тогда рукопожатие гарантирует гит, а не совпадение по часам. Но для начала `covers:` достаточно.

## Что ещё проверить перед реализацией

- [ ] Доступен ли коннектор **Microsoft 365** (OAuth на уровне аккаунта) облачным routine'ам — тогда часть с почтой можно вообще не морозить локально, а тянуть в облаке напрямую. Если нет — остаётся локальный сборщик.
- [ ] Скилл `weekly-vault-report` написан под локаль (абсолютные пути `C:\Users\RHL49\...`, локальный `fetch_mail.py`) — под облако нужен вариант с путями репозитория.
- [ ] Headless-запуск локального шага (`claude -p "..."`) не должен упираться в permission-промпты — все команды заранее в allowlist (см. [[permissions-unattended]]).
