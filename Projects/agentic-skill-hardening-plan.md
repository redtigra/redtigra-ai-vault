## 1. Контекст — что уже построено (база, от которой идём)

Скилл **`/harden-skill`** (`~/.claude/skills/harden-skill/`) уже работает и забэкаплен в repo `redtigra-claude` (коммит `023e02a`). Это пост-фактум починка unattended-скилла, который споткнулся о промпт пермиссии, чтобы **следующий** прогон был чистым.

**Готовый пайплайн `/harden-skill <name>`:**
1. Диагноз из `~/.claude/permission-requests.log` (объективный оракул) через `tools/perms.py` — не гадать.
2. Выбор фикса по ситуации, только узкий/неразрушительный:
   - **(A)** легитимная команда, не в allow → узкое per-script правило в `settings.json` (user-global, НЕ local);
   - **(B)** команда варьируется/не allow-listable → правка самого скилла.
3. **Независимый ревьюер-subagent** (general-purpose) обязан вернуть `APPROVE` до применения — не self-review.
4. Применение → валидация `tools/jsoncheck.py`.
5. Бэкап через `/save-skill`.
6. Отчёт через `log_report.py` в `hardening.log` (runtime-журнал, gitignored).

**Помощники (детерминированные, prompt-free):**
- `gen_rules.py` — печатает правило во всех комбинациях слэшей (exe fwd/back × script fwd/back × PowerShell/Bash), `--from-log` берёт скрипт из последнего промпта.
- `log_report.py` — append блока отчёта в журнал.

**Обкатано вживую (каждый фикс проверен оракулом):**
- `weekly-vault-report` — случай B: перечисление волта переведено с `powershell Get-ChildItem` на инструменты Glob/Read (pre-approved, в лог не пишутся).
- `save-skill` — случай B ×2: (1) убраны кавычки вокруг `git -C` пути (ломали якорный матчинг против некавыченных правил); (2) `Copy-Item`/`New-Item` заменены на фиксированный `copy_skill.py` под узким правилом.

**Непустой факт про матчер (записан в память `feedback_powershell_permission_matching`):** broad-правила PowerShell-cmdlet'ов (`Copy-Item *`, `New-Item -ItemType Directory *`) в этой среде **не срабатывают** надёжно, а per-script python-правила — срабатывают. Точная причина не установлена (гипотеза: cmdlet с `-Recurse`/`-Force` трактуется осторожнее). Вывод: не полагаться на broad cmdlet-правила; выносить файловые операции в фиксированный `.py`.

**Область (unattended-скиллы):** `generate-invoice`, `generate-quote`, `mail`, `weekly-vault-report`, `process-finance`.

## 2. Цель этого плана — замкнуть контур без ручного запуска

Сейчас `/harden-skill` запускается **человеком** пост-фактум. Чтобы стало «полностью agentic», не хватает **самозапуска**: чтобы система сама замечала новый `PERMISSION_REQUEST` от unattended-скилла и запускала харденинг.

Оценка на шкале agentic (обсуждалось): мы **на верхней половине** — есть цель-а-не-инструкция, инструменты, петля обратной связи через оракул, делегирование (ревьюер-subagent), персистентность (память/журнал). Не хватает последнего шага — замыкания контура без нажатия.

---

## 3. Согласованные решения

**Триггер = «после unattended-работ»** (детали механики — см. §4.3).
→ **Важное следствие:** отпадает нужда в планировщике (cron/Task Scheduler) и весь риск «локально vs облако». Облачная routine из `/schedule` не увидела бы локальный лог/`settings.json`/скиллы. А запуск локальный, в том же прогоне/сессии. Подводный камень снят самим выбором триггера.

**Модель доверия = semi-auto.** Агент сам диагностирует, гоняет ревьюера и готовит **точный фикс + отчёт**, но **НЕ применяет**. Тебе приходит готовый diff на одобрение. Правку файла **пермиссий** санкционирует человек (это security-чувствительно — в [[mail-permission-prompt-handover]] описан аудит, который broad-правила *удалял*).
→ Роль пользователя: из «оператора, жмущего да на каждом шаге» → в «владельца, ревьюящего результат».
→ Побочно: раз скан только читает и готовит черновики (draft-only), его **безопасно** вешать на автозапуск в хвост — он ничего не мутирует.

## 4. Архитектура (что достраиваем к harden-skill)

### 4.1 `scan.py` — детерминированный детектор
Философия как у `gen_rules.py`. Только чтение, кроме двух служебных файлов.
- Читает `permission-requests.log` от **водяного знака** (`scan-state.json` — как `~/.ms_graph_mail_state.json` в `/mail`, см. [[finance-reconciliation]]).
- Берёт только новые `PERMISSION_REQUEST`, двигает знак вперёд.
- **Атрибуция** (какой скилл споткнулся):
  - команда содержит путь скрипта `skills/<name>/...` → имя скилла напрямую;
  - shell-команда по ключам пути (напр. `diaries` → weekly-vault-report);
  - что не мапится однозначно → метка «нужен человек» (triage), **не гадать**.
- Отобранные unattended-случаи кладёт в **очередь ожидающих** `pending.json`.

**Статус 4.1 (2026-07-20): dry-run готов и проверен на реальном логе (258 записей).** Первая эвристика была слишком жадной — в скилловые корзины лезли dev/бэкап-команды, лишь упоминавшие папку скилла. Две правки закрыли это:
1. **фильтр шума** `is_noise()` — игнор команд с `redtigra-claude`/`scratchpad`/`Temp\claude`, ведущим файл-/VCS-глаголом (`cp`/`Copy-Item`/`Move-Item`/`Remove-Item`/`mkdir`/`New-Item`/`Test-Path`/`git`/`unzip`/`Start-Process`), или `python -c`;
2. **только первый путь** `skills/<name>/` (запускаемый скрипт), а не путь из аргумента.
После правок атрибуция чистая: weekly-vault-report и process-finance ловятся по своим настоящим рантайм-командам, ложная привязка ушла. **Ограничение:** у process-finance надёжный сигнал — только запуски его скриптов; шелловые команды по финансовым папкам почти всегда интерактивный реорг → справедливо в triage, не в фикс.

### 4.2 Режим скана в `/harden-skill` (semi-auto)
Для каждого нового случая из очереди: диагноз → черновик фикса (A: правило через `gen_rules.py` / B: правка скилла) → **ревьюер-subagent** → **стоп перед применением**. Все черновики + вердикты ревьюера собираются в **отчёт ожидающих**, остаётся в очереди. В момент скана (возможно, без человека рядом) работает молча.

### 4.3 Как это стартует — механика триггера (ВАЖНО: не фоновый демон)
Нет отдельного процесса, который «сидит и смотрит». «Старт» — это два разделённых слоя:

**Слой 1 — обнаружение, ЖЁСТКО (харнесс, не зависит от дисциплины агента).**
`Stop`-хук в `settings.json` дёргает `scan.py` в конце каждой сессии. `scan.py` детерминированно читает лог от водяного знака, атрибутирует новые промпты и кладёт в очередь `pending.json`. Срабатывает всегда — даже если прогон unattended-скилла оборвали на середине. Дёшево и безопасно (только чтение + запись очереди/знака). Существующий `PermissionRequest`-хук уже пишет каждый промпт в лог — это готовый «сенсор»; `Stop`-хук лишь превращает его записи в очередь.

**Слой 2 — черновая правка, МЯГКО (агентский ход, под semi-auto).**
Диагноз → ревьюер-subagent → черновик фикса — это работа **агента**, а не shell-скрипта, значит она не может быть чистым хуком. Стартует, когда агент жив в сессии и видит непустую `pending.json`: либо потому что unattended-скилл в хвосте SKILL.md зовёт разбор очереди, либо потому что пользователь зашёл в сессию. Применение — всегда под финальное «применить» человека.

**Почему не headless `claude -p` из хука:** это самый автономный вариант (хук сам поднимает отдельного агента чинить), но самый тяжёлый, с рисками конкурентности (фоновый Claude правит файлы, пока ты работаешь) и непроверенной надёжностью на этой Windows-машине. Отложено; при semi-auto он всё равно только готовил бы черновики.

**Итог по «старту»:** обнаружение перестаёт зависеть от того, «вспомнил» ли агент хвостовой шаг (это делает `Stop`-хук); починка остаётся на агентском ходу под ручное одобрение — ровно там, где и должна при semi-auto. Скан не рождает прогоны из ниоткуда — первичный запуск скилла всё равно от пользователя/расписания.

### 4.4 Разбор очереди (человеческий гейт)
Когда пользователь в контуре: одна команда показывает все накопленные черновики с готовыми diff'ами и вердиктами. Одобрение → применение существующим путём harden-skill (правка settings/скилла → `jsoncheck` → `/save-skill` → `log_report`) → очередь чистится.

## 5. Открытые вопросы / риски

- **Надёжность атрибуции.** Эвристика по путям покроет явные случаи; неоднозначные честно уходят в triage, а не в тихую догадку. Нужна проверка на реальном логе.
- **Жизнь очереди между сканом (unattended-момент) и разбором (когда человек рядом).** Фиксы копятся черновиками → разбор должен быть беспроблемным (одна команда, всё видно с diff'ами).
- **Первый прогон эвристики** обязателен на текущем логе (там уже есть кейсы weekly-report и Copy-Item) — до того как вешать триггеры на хвосты скиллов.
- **Дисциплина водяного знака** — как в `/mail`: ad-hoc не должен терять/дублировать записи; знак двигать только на успешном проходе.

## 5.5 Наблюдаемость / анализ (слой метрик)

Чтобы «усовершенствовать» было по данным, а не по догадкам. Уже пишется: `permission-requests.log` (сырой оракул), `hardening.log` (журнал действий), git-история фиксов. **Не хватает размеченных сигналов решений** — их добавляем.

**Лог событий:** `~/.claude/skills/harden-skill/harden-events.jsonl` — одна JSON-строка на событие, append-only, локальный, gitignored (как `hardening.log`).

**Типы событий и кто пишет (два писателя = два слоя старта):**
- `scan`, `recurrence` — **пишет `scan.py`** автоматически (жёсткий слой, Stop-хук).
- `draft`, `decision`, `verify` — **пишет агент** через помощник `log_event.py` (мягкий слой). Вызовы `log_event.py` **встроены в шаги SKILL.md** режима скана, чтобы запись была частью процедуры, а не «не забуду».

**Помощник `log_event.py`** (брат `log_report.py`): `--event <тип>` + `--set key=value` (скаляры) + `--json '<obj>'` (числа/списки/вложенное); `ts` и `event` подставляются сами; `ensure_ascii=False` → кириллические причины читаемы.

**Точка захвата `decision` — команда разбора очереди** (§4.4). Если фикс применён мимо флоу — запись не появится; золотой сигнал собирается только через очередь.

**Самое ценное — `draft.reviewer` + `decision.outcome`:** пара `reviewer=APPROVE` + `outcome=rejected` = ревьюер пропустил то, что человек забраковал → сигнал недокалибровки гейта (данные для перехода к full-auto когда-нибудь).

**Шаг «анализ»** (позже): маленький скрипт читает JSONL и печатает метрики — точность attribution (applied vs rejected), согласие ревьюер↔человек, дюрабельность/рецидивы фиксов — плюс рекомендации что подкрутить. Накопительный аналог `feedback_skill_run_analysis`.

**Риск, который эти данные и стерегут:** если скан стабильно тянет лишнее → шумная очередь → усталость одобрения → эрозия человеческого гейта. Метрики точности ловят этот дрейф рано.

## 6. Порядок стройки (предложенный)

1. ✅ **`scan.py` dry-run** + проверка эвристики на текущем логе — ГОТОВО (см. §4.1, статус).
2. **`log_event.py`** + `harden-events.jsonl` (слой наблюдаемости) — писать `scan`/`draft`/`decision`/`verify` с первого дня. ← строим сейчас.
3. **Очередь + знак** — формат `pending.json` и `scan-state.json`; `scan.py --commit` пишет в них + эмитит событие `scan`.
4. **Режим скана** в harden-skill (диагноз → черновик → ревьюер → стоп) + формат отчёта ожидающих; пишет `draft`.
5. **Команда разбора очереди** (показ diff'ов + одобрение + применение существующим путём harden-skill); пишет `decision` + `verify`.
6. **`Stop`-хук** (слой 1) в `settings.json` → гоняет `scan.py` в конце сессий. Только после того как шаги 2–5 проверены, чтобы жёсткое обнаружение не наполняло очередь до готовности разбора.
7. ✅ **Шаг «анализ»** — `analytics.py`: метрики по `harden-events.jsonl` + `pending.json` (объём сканов, точность attribution, согласие ревьюер↔человек, дюрабельность/рецидивы, разбивка по скиллам, рекомендации). Коммит `423b222`.

Каждый шаг — сам через дисциплину harden-skill (узко, ревьюер, проверка оракулом, бэкап). Служебные файлы (`pending.json`, `scan-state.json`, `harden-events.jsonl`) — gitignored, как `hardening.log`.
