# Handover — Захват километража одометра (прототип)

> Ранняя стадия, только спроектировали. Идея: снизить фрикшн в учёте километража автопарка RH247 — инженер фоткает одометр, vision-модель читает km, строка → CSV → позже Postgres. Сейчас скоуп **сознательно узкий: личный прототип для проверки идеи**, не раскатка на инженеров. Связано с [[session-management]].

## Зачем

В RH247 учёт километража высокофрикционный: инженеры ленятся вводить показания одометра руками, поэтому данные неполные (в приложении пробег подтягивается из SVR / ручного KM Update — см. модуль Cars). Долгосрочная цель — захват «одно фото + один тап», который сам превращается в CSV, загружаемый в Postgres.

Но **прежде чем что-то раскатывать, надо проверить саму идею** на личном прототипе для одного человека.

## Скоуп сейчас

Личный прототип для меня одной. Без хостинга, без телефонного приложения, без PWA, без нескольких пользователей, без логина. Цель — понять, работает ли ядро.

## Зафиксированные решения

- **Telegram** — в организации не используется, отпадает как канал.
- **WhatsApp Business** — отброшен. Технически возможен (Cloud API создаёт бизнес-аккаунт с нуля, инженерам нужен только обычный WhatsApp, а их номера уже есть в профилях RH247 — поле WhatsApp), НО упирается в организационную возню с Meta Business Manager + верификацией. Аппетита нет.
- **Приложение RH247 внешнее и под дев-командой** → в прототипе не интегрируемся. Следствие: машину нельзя автоматически вывести из назначения инженера, поэтому в прототипе — выбор из маленького личного списка.
- **Механизм доставки** (телефон / веб / PWA) отложен: сначала проверяем ядро, потом упаковка.
- **Режим работы:** Claude собирает руками через свои инструменты, **с остановками и объяснением на верхнем уровне** (что делаем и зачем), **без разбора кода**. Пользователь нетехнический — принимает продуктовые решения и делает только то, что нельзя автоматизировать (дать фото, завести аккаунт/ключ).

## План (стадии)

- **Stage A — make-or-break.** Прочитает ли vision-модель (Claude API) одометр по реальным фото — LCD-блики, аналоговые барабаны, грязь, срезанные цифры? Дать несколько реальных фото, сверить распознанное с известными числами, решить go / no-go. **Строить почти нечего — эта стадия решает всё.**
- **Stage B — ядро.** Простой инструмент на моей машине: фото → число прочитано → показано → подтвердил/поправил → строка в CSV. С проверкой монотонности (`new_km >= last_km` для этой машины).
- **Stage C — отложено.** Только если A и B прошли: удобный захват (веб/телефон/PWA), раскатка на инженеров, Postgres.

## Модель данных (одна строка = одно снятие)

```
reading_id    text        сгенерирован
captured_at   timestamp
plate         text        машина — из маленького личного списка (или одна машина)
odometer_km   integer
photo_path    text        путь к файлу, не сам блоб
source        text        ai_suggested | manual
confidence    number      от vision-модели
note          text
```

CSV = append-only источник истины; фото лежат в папке; Postgres — позже (колонки CSV = будущие колонки таблицы).

## Следующий шаг при возобновлении

Старт **Stage A**: я даю горсть реальных фото одометров → проверяем точность распознавания против настоящих чисел → решаем, стоит ли идти в Stage B.

## Открытые вопросы / отложено

- Механизм доставки для инженеров (веб-страница → PWA на телефоне) — вся упаковка ради «одного тапа».
- Инференс машины из назначения RH247 — требует доступа к дев-команде, которого сознательно избегаем.
- Postgres-загрузчик (`\copy`), multi-user, оффлайн-очередь.
