# Расследование без запросов подтверждения: `tools/permlog.py` и правило read-tools

Сессия 2026-07-29. Исходная жалоба была бытовой: «когда я прошу что-то исследовать, во временном каталоге пишутся скрипты на Python, и каждый требует подтверждения — любой вопрос превращается в бесконечное нажатие кнопок». Разбор показал, что дело не в строгости настроек, а в структурном изъяне.

## Диагноз: одноразовый скрипт невозможно внести в список разрешённых

Путь временного каталога сессии (scratchpad) содержит её **уникальный идентификатор**:

```
...\Temp\claude\C--Users-RHL49-claude-work\44215cb2-2da8-426a-a5d1-ac799b7e08da\scratchpad
```

В каждой новой сессии он другой. Разрешающие правила (allow-rules) сопоставляются с командой **буквально**, посимвольно — см. [[chaining-guardrail-hook]]. Значит, устойчивого правила для одноразового скрипта **не существует в принципе** — это следствие устройства системы, а не недостаток настройки. Каждый такой скрипт стоит одного запроса подтверждения, и так будет всегда.

Напрашивающееся решение — разрешить весь временный каталог подстановочным шаблоном — отвергнуто: оно даёт молчаливое одобрение **любому** только что сочинённому коду, то есть ровно той свободе действий, ради ограничения которой запросы подтверждения и существуют.

## Свидетельство: девять скриптов, один и тот же разбор журнала

Параллельная сессия исследовала как раз систему разрешений. В её временном каталоге лежало девять скриптов:

```
analyze_perms.py  classify_perms.py  rules_audit.py  rate.py  today.py
semantics.py      hooktest.py        denytest.py     gitwildcard.py
```

**В четырёх из них дословно повторялись одни и те же пятнадцать строк**, разбирающие журнал на записи. Скопированы без единого изменения. Девять подтверждений, чтобы ответить на один вопрос.

Пригодными для повторного использования оказались четыре скрипта. Остальные — `semantics`, `hooktest`, `denytest`, `gitwildcard` — были разовым исследованием того, как ведут себя правила при попытке внедрения команд, и в инструмент не вошли.

## Решение: три уровня

**1. Чтение и поиск не требуют скрипта вообще.** Инструменты Read, Grep и Glob не являются командной оболочкой, подтверждения не требуют и покрывают содержимое файлов, поиск по регулярному выражению и обход каталогов. Большая часть работы вида «разберись с X» состоит из этого целиком. Python нужен лишь тогда, когда что-то действительно надо *вычислить*: разобрать, сгруппировать, сосчитать, сопоставить.

**2. Если одно и то же вычисляется во второй раз — это уже инструмент.** Не скрипт во временном каталоге, а файл в `~/.claude/tools/`: проверен однажды, разрешён однажды (каноническая пара правил), дальше работает молча. Образец был и раньше — `perms.py`, `jsoncheck.py`, `docx_text.py`.

**3. Использовать готовое, а не писать заново.** Модуль `harden-skill/match_rule.py` уже отвечает на вопрос «покрыта ли команда правилом». Его следует импортировать, а не воспроизводить.

Всё это записано в `~/CLAUDE.md` как базовое правило «Investigate with read tools, not scripts».

## Инструмент `tools/permlog.py`

| Команда | Назначение |
|---|---|
| `list` | записи журнала; отбор по `--day`, `--since`, `--tool`, `--kind`, `--grep` |
| `stats` | число подтверждений по дням и доля от всех вызовов оболочки |
| `top` | какие команды вызывают подтверждение чаще прочих (по началу строки или `--exact`) |
| `rules` | разбор `settings.json`: повторы, разрастание вариантов записи, правила на удалённые скрипты |
| `recheck` | перепроверка **прошлых** подтверждений против **текущего** набора правил |

Наиболее ценна `recheck`, унаследованная от `today.py`. Она выносит три вердикта: `COVERED`, `NOT-COVERED` и `PREFIX-BUT-SEGMENTS` — последний означает, что правило совпало с началом команды, но команда является цепочкой, а среда исполнения требует разрешения на каждое звено по отдельности. Исторически это самый запутывающий случай, поэтому он назван явно. Самопроверка (`--test`) проходит полностью: 12 из 12.

Правила были добавлены **до** первого запуска, поэтому даже он обошёлся без подтверждения. Проверено объективным источником — журналом: `permlog list --kind PERMISSION_REQUEST --grep permlog` не вернул ничего.

## Что обнаружилось попутно

- **Главный источник подтверждений — код, встроенный прямо в командную строку** (`python.exe -c "..."`): не менее 42 случаев из 192 за неделю. Такое невозможно разрешить заранее, поскольку это произвольный код в аргументе. Лечится только привычкой так не писать.
- **192 подтверждения на 1041 вызов оболочки (18%)** за период с 20 по 27 июля. В день самого расследования доля достигла **56%**.
- **452 разрешающих правила**, из них 269 приходятся на 30 скриптов — это на **210 больше** нормы в два правила на скрипт. Шесть правил записаны неверно. Одно, в `settings.local.json`, ссылается на несуществующий `generate-invoice/gen_invoice.py`. Уборка вынесена в отдельную задачу.

## Ошибки, допущенные по ходу

- Первый commit получил мусорный символ `@` в заголовке: многострочная строка была записана в синтаксисе PowerShell (`@'...'@`), а команда выполнялась через Bash. **Такая конструкция принадлежит PowerShell; в Bash нужен heredoc.**
- Heredoc, в свою очередь, был отклонён перехватчиком `block_chains.py`: тот делит команду по строкам, а строки тела сообщения не начинались с `git`. Обходной путь — записать сообщение в файл и передать его как `git commit -F <файл>`. Сам перехватчик стоит доработать.
- `settings.json` правился параллельной сессией прямо во время работы: между чтением и правкой номера строк сместились на две. Вставка выполнялась по якорной строке, а не по номеру, и потому уцелела. Общий вывод: **при живой второй сессии править конфигурацию только по текстовому якорю.**
